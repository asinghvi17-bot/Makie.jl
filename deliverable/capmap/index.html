Makie 0.25 + WGLMakie compiled fully to WebAssembly: what works and what doesn't

WasmCodegen.jl main @316bbaf · verify=:error, host=:wasi, Config(shell_first_mutables=true), trim=:safe · Julia 1.13.2 · 2026-11-07

Short answer.
  • Works now. These plots pass a strict compile when they are built at build time and only updated at runtime. Their WGLMakie update messages are byte-identical to native: scatter, lines, linesegments, image, heatmap, surface, volume, meshscatter, band, errorbars, and a user @recipe. text also works, with a prerendered atlas.
  • Fails in the update path: mesh, poly, barplot, hist, pie, contourf, arrows, contour, voxels, and the Axis block.
  • Fails for every type: creating plots at runtime (599 errors for scatter!) and deleting them (150 errors for delete!).
  • Interaction: cam2d has 6 errors. Every Julia-side interaction also needs a JS↔wasm bridge, which does not exist yet.
  • Most failures are type-stability problems that can be fixed upstream (class a). Only two failures were WasmCodegen gaps, and both have workarounds.

1. Setup and method

  • Makie stack (local merges, not pushed): trim/computepipeline-static-dispatch @37cb4114 merged with trim/axis-typed-access @e2f01244. The latter already contained fix/axis-025-native-bugs @0adccd44.
  • Other packages: WasmCompat.jl feat/observables-ext @8df2164 and WasmHost.jl feat/browser-adapter @8b9340c. Bonito is v5.3.0.
  • Each probe is a small program in deliverable/probes/p_*.jl:
    1. It builds a Scene or Figure at build time. Then it runs WGLMakie.serialize_three on every atomic plot, which registers WGLMakie's wgl_renderobject / wgl_update_obs nodes.
    2. It attaches a recorder to each wgl_update_obs.
    3. At runtime, main() sets plot inputs and polls p[:wgl_renderobject][], as WGLMakie's poll_all_plots does. It prints a digest of every Bonito.LargeUpdate.
    The same program runs natively (native.jl) and as wasm under node:wasi (run.mjs), and the two outputs are diffed (probe.sh).
  • Closed world. ComputePipeline.StaticDispatch.install! is limited to the probe's live inputs and outputs. WasmCompatObservablesExt.close_world! is called on the scene and the update observables (common.jl).
  • Argument types. Arguments are given already in their converted types (fixed point). This avoids convert_arguments recursing through Any (conversions.jl:13-26), which accounted for 392 errors in the first image probe.
  • Labels: PASS = strict compile succeeded and the output is identical to native. FAIL n = n verifier errors. PASS* = passes with build-time overrides of class (b). untested = not probed; the reasoning given comes from reading the code.
  • Blocker classes: (a) upstream type fix; (b) build-time override or generator; (c) WasmCodegen gap; (d) fundamental to a closed world.
  • All passing probes were re-run with the final override set as a regression sweep (probes/out/summary.txt, after the "FINAL SWEEP" marker).

3. Text and fonts

What fails

Without overrides, text fails with 220 errors. In order of appearance:

  1. Atlas. The TextureAtlas struct and its deserialization of the cached atlas (texture_atlas.jl:4, 107-108), and rendering new glyphs at runtime: render → renderface → FreeType (texture_atlas.jl:376-407, :393).
  2. BezierPath markers: bezier.jl:205-224, 809.
  3. FreeType calls during layout. These are ccalls and loads of C structs. For each character, layout_string (text_layouting.jl:113-122) calls find_font_for_char (texture_atlas.jl:239), FTA.glyph_index and get_extent. FTFont.getproperty does an unsafe_load of FT_FaceRec.
  4. Other paths:
    • the _positions callback (text.jl:68-85) uses Core._typevar, which is a WasmCodegen gap (c);
    • the _placed_text_specs plotlist! path deep-copies a Vector{PlotSpec} (ComputePipeline.jl:683);
    • WGLMakie's glyph_data is a Dict{Symbol,Any} compared with is_same (plot-primitives.jl:443).

In WGLMakie as shipped, the browser never rasterizes glyphs. WGLMakie's TextureAtlas.js (lines 60-106, 139-142) only receives SDF tiles that Julia rendered, so every new glyph must come from the wasm side, unless the host supplies it (routes B and B′ below).

Does a prerendered atlas work? Yes (probed: p_text_atlas.jl)

text_overrides.jl works as follows:

  1. At build time, natively, it records for each font the face fields the layout reads, a Char → glyph index table, and the extent caches. It also renders every glyph of a chosen character set (here ASCII 32-126) into the atlas.
  2. It overlays, for Wasm only: FTA.glyph_index, getproperty(::FTFont), get_extent, find_font_for_char, get_texture_atlas and insert_glyph!. The overlays are table lookups, and a miss raises a clean error.
  3. Two smaller overrides replace the _positions callback with typed predicates and stub the empty-spec plotlist!.

Results:

  • Strict compile passes.
  • Runtime strings made of characters that were not in the build-time string but are in the prepared set give updates identical to native.
  • Outside the set, "Ω" raises character not in the build-time glyph set: Ω, as designed.
  • The only other diff: glyph_data is resent on every update because the is_same override always reports a change.
  • Module size: 10.1 MB, 1.9 MB gzipped. Most of this is the 2048² Float16 atlas (8 MiB). An atlas with only the glyphs used would make it much smaller (estimate, not measured).

Letting the browser do the font work: routes B, B′, C and C′ (probed)

The question: can a JS solution give Julia the SDFs and the font metrics, and can a different text layouter emit a text type that needs no SDF at all because the browser draws the glyphs? Four routes were built and measured. (“Route B/B′/C/C′” here are not the A/B/C/B′ columns of §2.) The first two probes (B and C) are on branch trim/text-browser of asinghvi17-bot/makie.jl, the follow-ups (B′, C′) on top of it. Setup: the same Makie merge as in §1; WasmCodegen feat/task-park-host-wait @467d91e here (§1 used main @316bbaf), WasmCompat @8df2164, WasmHost @5cb54e3 plus the text jobs, verify=:error, host=:wasi, trim=:safe, shell_first_mutables=true, no wasm-opt (optimize=nothing); headless Chromium 158 and Node 26. Route B′: what was measured

Interface. One host import pair, wasm_host.text_start(req, len) → handle and text_finish(handle, buf, cap) → len, with the same start/finish shape as WasmHost's http_start/http_finish. Request kinds: font (ascender, descender, line height), extent (advance and ink box), sdf (codepoint, pixel size, downsample, padding) and measure. An sdf response is Makie's sdistancefield(bitmap, downsample, pad) tile as little-endian float32 plus the glyph's metrics. The module parks on the handle (Runtime.Host.await_handle; JSPI in a browser) because loading a font face is asynchronous. A variant for fonts that are already loaded could be a plain synchronous import; it was not built. On the Julia side, the overlays are the ones from the first probe (FTA.glyph_index is the codepoint, get_extent, getproperty(::FTFont) and find_font_for_char from the host) and insert_glyph! takes the tile from the host. Makie is not modified.

SDF code. The JS side vendors edt/edt1d from @mapbox/tiny-sdf 2.3.0 (BSD-2-Clause, license header and file kept) and nothing else. Makie's SDF is the exact Euclidean distance to the nearest inside pixel minus the distance to the nearest outside pixel on a binary image (coverage above 127.5), averaged over 5×5 blocks and divided by 5. The F–H transform computes the same exact distances, so the JS tile has to be the same number, not an approximation.

  • SDF difference, same bitmap. FreeType's 320 px bitmaps of 115 glyphs (ASCII, Greek, accented letters, punctuation) through the JS code against Makie's own tile: all 115 tiles have the same size and the maximum and mean absolute difference are exactly 0, including the blank glyph (Makie fills a tile of a bitmap without inside pixels with prod(size)/downsample; the JS port reproduces that).
  • SDF difference, the browser's own raster (Canvas2D in Chromium 158 at 320 px, then the JS SDF, against Makie's tile for FreeType's bitmap of the same glyph): 103 of 115 tiles have the same size as Makie's; the other 12 differ by one tile pixel in one direction because the browser bitmap's bounding box differs by one pixel (C G M O S w ( ; < > • #). On the 103: max |difference| 0.385, mean 0.021 (median of the per-tile maxima 0.185; worst glyphs Q, 5, @, ?, Ω). The unit is a tile pixel (the 64 px em, where the shader's anti-aliased edge is about 1 unit wide). On the 93 glyphs whose bitmaps have identical size: max 0.24, mean 0.012. After the atlas's Float16 storage the numbers are the same to three digits.
  • Time per glyph. JS SDF step: 3.4 ms mean in Node 26 on FreeType bitmaps (best of 5; max 8.1 ms); in Chromium 3.2 ms best-of-5 and 3.7 ms on the first call in a standalone page, 5.4–5.8 ms per glyph inside the module runs; against 34.4 ms for Makie's Julia SDF natively and about 700 ms in the compiled module. The browser's raster costs 0.6 ms. Whole compiled module, Chromium: 15 new glyphs 0.41 s, 36 glyphs 0.55 s, 90 glyphs 0.97 s (slope 7.6 ms per glyph; about 4 ms of each glyph is the module's own work: two parked jobs, parsing, packing); route B on the 36-glyph text: 26.6 s (739 ms per glyph). Node with the mock backend, 15 glyphs: 0.52 s against 8.1 s, and the two atlases are byte-identical in their printed statistics.
  • Wasm size. Strict compile clean for both. Route B′ module 4,741,203 bytes (975,218 gzipped), route B 4,786,737 (997,213): −45,534 bytes (−0.95 %), −21,995 bytes gzipped (the SDF code, SignedDistanceFields.jl, is gone). Unoptimized; with an empty atlas (no 8 MiB Float16 image), so both are well below the 10.1 MB of the prerendered-atlas module (not the same program). Build 255 s with 1.9 GB peak RSS (B: 304 s, 1.9 GB).
  • A text! scene, strictly compiled, run in Chromium. text! built at build time with “hello”, changed at run time to Wasm: ünï 42 ΩΣ ≈ ∞ (glyphs the module never saw: rc=0, 31 host jobs, 15 new tiles). Layout numbers equal native FreeType: all 19 glyph origins and advances identical (largest difference 0.000 at 3 decimals, font size 40), block bounding box identical (389.4 × 46.6), font ascender/descender/height 947/−218/1165 identical, ink boxes within 0.005 em.
  • Image difference to native. WGLMakie's own JS cannot display a Wasm module's output yet (no JS↔wasm session bridge, §6 #4), so the images come from the same Julia code run natively with the host's answers recorded from the real JS adapter in Chromium (runTextRequest + Canvas2D + sdfTile), displayed by WGLMakie in headless Chromium and compared with the same figure on FreeType. The text probe's printed output is identical between that run and the compiled module in Chromium, so the atlas and layout are the module's. Two native screenshots of one figure are bit-identical (noise floor 0). Text scene (7 text plots: four sizes, bold, italic, rotated, accents, Greek): mean |gray difference| 0.29 of 255 over 600×260 px, 24 pixels above 32 (max 66). Axis with title, two axis labels and tick labels (600×400, 35 glyphs): mean 0.042, 3 pixels above 32 (max 45). To the eye the images are the same; differences are sub-pixel edge placement.
  • An Axis with tick labels does not compile strictly, for reasons that are not text. Capmap's Axis probe with the host's text in place of the prerendered atlas fails with 437 verifier errors (439 with the atlas): none of the failing statements is in the new code, at FreeType or in the atlas; 117 originate in Makie's text.jl (layout_text over input_text::Vector{Any}, :547, :155, :566), the rest are the §6 items (ComputePipeline, conversions, colormaps, Observables). The Axis comparison above is therefore the hosted-native run, not a Wasm module.

Limits of B and B′. Glyphs are addressed by codepoint, so anything that addresses them by FreeType glyph id or glyph name cannot be drawn: MathTeXEngine (LaTeX), math variants. Makie's font fallback chain is replaced by the browser's: document.fonts cannot say whether a face has a codepoint, so there is no “does this font have X”, and fallback fonts differ per machine. A text plot built natively keeps FreeType glyph ids, so a native-built plot has to be re-set before its glyphs are looked up. Metrics are read at 4000 px (Chromium on Linux rounds advances to whole pixels at small sizes), the browser's raster is not FreeType's (IoU 0.995, bounding box identical for 93 of 115 glyphs), and the page has to register the fonts. A JSPI-capable browser is needed for the parking design (Firefox and Safari had none when WasmHost's docs were written); not measured outside Chromium.

Route C and C′: browser-drawn labels

  • C (text_handler with measureText metrics, labels drawn by the DOM or Canvas2D over the canvas): strict compile clean, 2 host jobs, 0.5 s. A plain Axis matches native within sub-pixel shifts (mean |gray difference| 0.9–1.4 of 255; 0.34 for Canvas2D with text-rendering: geometricPrecision). It breaks 3D depth ordering (a label inside an opaque sphere is drawn over it), PNG export (canvas.toDataURL has no text), stroke/glow, per-glyph colours, and does not cover rich text or LaTeX. The Axis decorations need one blank glyph per line, because Axis sizes protrusions from per-glyph arrays.
  • C′ (canvas-texture sprite per label) keeps depth testing: yes. Each label is drawn with Canvas2D into a texture, and a quad is drawn by a ShaderMaterial that uses the 3D scene's own Makie camera uniforms (scene.wgl_camera.projectionview, resolution), anchored at the label's 3D point and sized in pixels. The label goes through the same depth buffer as the meshes, one depth per label (its anchor's), which is exactly what Makie's own markerspace = :pixel text does. Prototype: about 60 lines of JS added to the page, no change to Makie. In headless Chromium, in an LScene with an opaque sphere and three labels (inside the sphere, straddling the silhouette, above), the sprite scene reproduces native Makie text: the inside label is occluded, the straddling label is cut by the sphere, the label above is visible (mean |gray difference| 0.11 of 255, 357 pixels above 32 of 240,000, at glyph edges). After the camera is moved in the browser the labels follow with no Julia round trip, because the quad reads the camera uniform that OrbitControls updates. canvas.toDataURL contains the labels (bit-identical to the screenshot), unlike the DOM overlay. What still limits C′: the texture is rasterized at one pixel density (no re-rasterization on zoom or when a data-space label gets perspective-scaled), transparent sorting among several transparent objects is by object, not by label depth, labels are not in the picking pass, and clip planes and overdraw need handling in the shader. The layout, as in C, is the browser's and not Makie's, rich text and LaTeX still go through glyphs.
Recommendation (updated with the browser probes).
  • Runtime text in a browser: route B′. It is the cheapest way to arbitrary text. About 230 lines of Julia overlays and a JS adapter of about 300 lines (including the SDF, of which about 40 lines are tiny-sdf's), Makie unchanged, layout metrics equal to FreeType's for the bundled font, tiles within 0.4 tile pixels of Makie's, 8–11 ms per new glyph, no prerendered 8 MiB atlas, and the module is smaller than with route B. It replaces the build-time atlas whenever the host is a browser that can park the module.
  • Keep the build-time atlas for hosts without a browser (Node, wasmtime) or where the character set is closed. It needs no host at run time.
  • The pure-Julia CFF/TrueType stage (the former “Next”) is needed only for what B′ cannot do: LaTeX and other glyph-id/name users, deterministic text outside a browser, or no JSPI. It is no longer the main path for plain text.
  • FreeType-to-wasm remains the fallback for full fidelity at run time everywhere.
  • Route C/C′ as an opt-in for plain 2D or simple 3D labels where browser-quality text matters more than matching Makie's layout; C′ (not the DOM) if the label must be depth tested or exported. Neither handles rich text or LaTeX.
  • Whatever is chosen, the Axis is blocked by the §6 items, not by fonts.

4. Static path: typed plot constructors

Do @recipe attribute declarations carry types?

Syntactically yes, effectively no.

  • @recipe accepts attr::T = default, but the type is only stored in runtime vectors (DocumentedAttributes.jl:358-550).
  • For plots, every attribute becomes Computed(key) with set_type!(node, Any) unless the plot is primitive (DocumentedAttributes.jl:1220-1228). Only Blocks use the types (:1216-1218, add_typed_nodes!).
  • Typed positional arguments (@recipe Name (x::T, y::S)) generate types_for_plot_arguments (recipes.jl:318-342, :339). These are used only for validation and docs (interfaces.jl:49, compute-plots.jl:823).
  • The plot type alias is const Name{ArgType} = Plot{name, ArgType} (recipes.jl:451).

Where the types are lost (seams)

  • _create_plot / _create_plot! (figureplotting.jl:441, 484, 547) and default_plot_func → plottype(args...) (:438).
  • build_plot (compute-plots.jl:916-932): converted is Any, ArgTyp = typeof(converted), FinalPlotFunc = plotfunc(plottype(P, converted...)).
  • Attribute conversion nodes are AttributeConvert{Key,Plot} built from runtime Symbols (compute-plots.jl:709-717, 900-964). Theme lookups use Attributes (Any).
  • connect_plot! (compute-plots.jl:936-981) → plot!(plot), entered from plot!(scene, plot) (interfaces.jl:226-231).
  • kw = Dict([k => v for (k, v) in user_kw if k in used_attr]) (compute-plots.jl:819).
  • Edge-callback reflection: Base.which(f, arg_types) (ComputePipeline io.jl:85) — 130 of the 599 runtime-scatter! errors.
  • WGLMakie insertion: insert_plot! → Bonito.evaljs_value (display.jl:500) — a synchronous round trip to JS.
Verdict: feasible, as a build-time generator. It works the same way as StaticDispatch.install! and close_world!, which already produce passing builds:
  1. The app declares the call shapes it will make at runtime (plot function, argument types, attribute keys and types). The generator runs them natively once.
  2. It records the concrete Plot{F,ArgTyp}, the converted types, the resolved attribute and theme values, the edges created by plot!, and the children.
  3. It emits typed constructor methods as Wasm-only overlays, for example static_plot!(parent, ::Val{:image}, x::T1, y::T2, img::T3, kw::NamedTuple{K,V}). These build the graph with concrete Computed types and call the recorded edge callbacks directly.
Class (b) for the generator. The Any-widening it replaces is (a) and could be fixed upstream instead. Nothing found is (d), apart from types the build never saw (new user closures or recipe types at runtime).

Prototype plan: image + barplot

  1. image.
    • Record build_plot(Image, scene, (x,y,img), kw) natively. Emit a typed build_plot, add_attributes! with the recorded node types, and connect_plot!. The default argument conversion is already known to compile, from the fixed-point probe.
    • Run StaticDispatch.install! against the template plot's graph, so that later instances of the same type reuse the hooks.
    • Overlay Base.which at io.jl:85 to return the recorded location (b). Replace argument_error / kw Dict at compute-plots.jl:819 with the recorded key set.
    • For WGLMakie: replace insert_plot!'s evaljs_value (display.jl:500) with a host import that posts the serialized plot to the JS client. WasmHost's browser adapter has no Bonito comm bridge today.
  2. barplot. Do the same for BarPlot and its children (poly → mesh + lines, and optional text). First fix the mesh merge and expand_faceviews typing (conversions.jl:595-617, poly.jl:175-176), because barplot fails even in column A.
  3. Size. Task 055a3d4b needed about 500 lines of hand overrides per plot type and still had 215 errors left. A generator should amortize that to about 1-1.5 k lines once, plus a declaration per call shape (estimate).

5. Interaction

WGLMakie's JS client sends DOM events to Julia through a Bonito comm (comm.notify, WGLMakie.js:382-515). connect_scene_events! (events.jl:55-120) writes them into events(scene) observables inside @async (events.jl:58). Under wasm this requires:

  1. a host bridge that pushes JS events into an exported wasm entry. WasmHost feat/browser-adapter provides WASI + JSPI, not a Bonito comm;
  2. either tasks=:jspi or an override that drops the @async.
